# 收集型系统：实体性质推导指引

> 配合五步法 Step 4 使用
> 理论基础：perspective-dependent-property-emergence（视角依赖的属性涌现）

## 核心原则

实体沿任何维度特化后，特化视角的**目的**蕴含该视角专属的属性需求。这些属性在通用视角下不可见，只有"进入"特化视角后才能发现。

**操作口诀**：对每个维度的每个值，问——"这个特化存在的目的是什么？目的需要什么独有信息？"

## 推导流程

### 第一步：列出实体清单

列出系统管理的所有实体类型。收集型系统的实体通常分三类：

| 实体角色 | 说明 | 典型例子 |
|:---|:---|:---|
| **被收集对象** | 系统核心管理的实体 | 资产、知识条目、告警、日志 |
| **采集基础设施** | 支撑收集过程的实体 | 任务、通道、适配器、采集规则 |
| **管理辅助** | 辅助管理的参考数据 | 分类码表、标签、策略模板 |

### 第二步：对每个被收集对象，逐维度推导

#### 维度 A：生命周期阶段

```
对每个阶段，问：
  "这个阶段的目的是什么？"
  "为了完成这个目的，需要什么独有信息？"
```

**推导模板**：

| 阶段 | 目的 | 蕴含的专属属性 | 蕴含的专属操作 |
|:---|:---|:---|:---|
| 暂存/待确认 | 暂时持有，等待审核 | sourceParty, discoveredBy, discoveredAt | 确认、忽略、合并 |
| 正式/活跃 | 正式纳管，持续维护 | credential, lastVerifiedAt, managedBy | 编辑、停用、关联策略 |
| 归档/退役 | 保留记录，不再活跃 | archivedAt, archiveReason, retentionPeriod | 恢复、永久删除 |

#### 维度 B：实体主类型

```
对每个主类型，问：
  "这个类型的本质特征是什么？"
  "这个特征需要哪些专属字段来描述？"
```

**推导模板**：

| 主类型 | 本质特征 | 蕴含的专属属性 |
|:---|:---|:---|
| （填入具体类型） | （填入特征） | （推导属性） |

#### 维度 C：来源通道

```
对每个来源通道，问：
  "这个通道的特殊性是什么？"
  "通道特殊性是否带来额外的元数据？"
```

**推导模板**：

| 来源通道 | 通道特殊性 | 额外元数据 |
|:---|:---|:---|
| 自动扫描 | 有发现时间和扫描工具信息 | scanTime, scanTool, scanScope |
| 第三方同步 | 有同步批次和外部 ID | syncBatchId, externalId, syncProtocol |
| 手动录入 | 有操作人和录入原因 | operator, entryReason |
| 设备上报 | 有设备信息和上报时间 | deviceId, reportTime, deviceProtocol |

#### 维度 D：管理角色

```
对每个管理角色，问：
  "这个角色对其他实体有什么约束？"
  "约束是否需要额外字段来表达？"
```

### 第三步：汇总为属性并集

所有维度推导出的属性，汇总为实体的**完整属性集**（并集）。并为每个属性标注"属于哪个维度"（即 applicableTo / modes 标注）。

```
完整属性集 = 通用属性（所有视角共享）
            ∪ 生命周期阶段专属属性
            ∪ 主类型专属属性
            ∪ 来源通道专属属性
            ∪ 管理角色专属属性
```

### 第四步：输出为 model.yaml 可用格式

每个属性标注适用范围：

```yaml
fields:
  - code: sourceParty
    name: 来源方
    applicableTo: { lifecycle: [temporary] }

  - code: ipAddress
    name: IP地址
    applicableTo: { mainType: [ip, server] }

  - code: archivedAt
    name: 归档时间
    applicableTo: { lifecycle: [archived] }
```

## 常见陷阱

### 陷阱 1：在通用视角下枚举属性

错误做法：站在"资产"的通用视角列属性 → 只能看到 name, type, importance 等通用属性。

正确做法：切换到每个特化视角（临时资产、IP 资产、扫描发现的资产…），逐个推导。

### 陷阱 2：把推导出的属性当作"本体不稳定"

多视角推导出更多属性不是本体在变——本体是所有视角发现结果的**稳定并集**。新发现的属性是维护迭代，不是架构不稳定。

### 陷阱 3：跳过"目的"直接猜属性

错误做法：临时资产 → "它可能需要一个 expireDate"（凭直觉猜）。

正确做法：临时资产的目的是"暂时持有等待审核" → 审核需要知道"谁报上来的""什么时候报的""通过什么通道" → 推导出 sourceParty, discoveredAt, sourceChannel。

## 输出检查

推导完成后，用以下问题自检：

- [ ] 每个生命周期阶段是否都独立问过"目的→属性"？
- [ ] 每个主类型是否都独立问过"特征→属性"？
- [ ] 属性集是否标注了适用范围（哪个维度的哪个值）？
- [ ] 是否有属性出现在多个维度（说明可能是通用属性，应上提）？
