# Harvest Session

把一次协作留下的耐久结果送到正确位置。不要默认生成聊天纪要；“怎么走到这里”与“项目现在是什么状态”需要进入不同容器。

本 Skill 是开放语义的结构化 procedure，不是状态型 Workflow。步骤内部需要 Agent 判断，且没有持久化阶段、自动重试或机器强制能力。

## 先对账事实

若会话改变了仓库，读取项目规约、当前 diff/status、相关状态文件和验证结果。不要只根据聊天记忆宣布完成，也不要把未运行的验证写成证据。

建立五类事实：

1. 已完成的改动与产物；
2. 改变资产定位、边界或公共契约的决定；
3. 未完成事项、已知风险与阻塞；
4. 实际验证过的范围；
5. 没有查看、没有测试或没有改变的负空间。

## 按三问分诊

对每个值得保留的候选依次判断：

1. **身份问**：它是否改变某个资产“我是什么”的答案？是则确认就地文档或提交材料已有 3–5 行 why：触发事件、参照系、本次决定和排除项。
2. **复利问**：换一个项目仍有价值吗？否则只进入当前项目状态或交接。
3. **证据问**：是否有真实推导、运行结果或可解析来源？没有则标为待验证观测，不得包装成稳定知识。

## 进入已有容器

遵循当前项目的文件约定，不发明新的状态或关系 schema：

| 结果 | 优先容器 |
|:---|:---|
| 定位与边界 why | 被改资产附近的文档；若项目有提交规范，再进入提交材料 |
| 当前阶段状态 | 既有 `PROJECT-STATE.md`、`HOME.md`、`HANDOFF.md` 或项目指定状态文件 |
| 跨项目提炼候选 | 既有 backflow / ingest / candidate queue；没有容器时只在收割报告列出 |
| 环境与稳定约定 | 受版本控制的配置文件，以及项目规约中的短指针 |

不要把进行中状态写入 auto-memory，不要为了“留痕”新建内容重复的会话总结目录。

## 写入与副作用边界

- 用户明确要求收尾、保存或交接，或项目规约要求收尾写入时，可更新任务范围内的项目文件。
- 仅要求口头总结时，输出报告，不擅自写文件。
- 不自动 commit、push、发布知识、发送消息或修改项目外部 registry。
- 保留工作区中已有的用户改动；无法区分归属时只报告，不覆盖。
- 事实不足时明确写“未验证”或“未查看”，不补写推测。

## 输出收割报告

使用最小充分格式：

```markdown
## 收割报告

- 完成与证据：……
- 定位 why：已留 / 不适用 / 缺失
- 状态与交接：……
- 提炼候选：……
- 负空间：未查看……；未验证……
- 已更新文件：…… / 无
```

没有耐久候选且无需写文件时，简洁说明“本场无新增提炼候选，现有状态与 why 已对账”。
